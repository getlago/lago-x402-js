## [Unreleased]

### Added

- `createLagoX402(config)`: validates the config, then checks every route against Lago before it serves. The billable metric must sum the `value` property (`sum_agg`, `field_name: "value"`, no expression, not recurring), and a gate check without sign-in must answer a challenge with sign-in chains (lago-api with INT-331). A route Lago refuses rejects the boot with one `LagoX402ConfigError` naming every refused route and its reason, reported first (`onError(err, "boot")` and the log line) so the refusal is never silent, even when the promise is only awaited by a request; an invalid config rejects at once and is not reported. A route Lago cannot be reached for (5xx, 408, 429, timeout, network error, facilitator outage) answers 503 `unavailable` and is retried in the background (1 s doubling to 60 s, never keeping the process alive) until it becomes active, or is refused for good if Lago then refuses it.
- `x402.close({ timeoutMs })` (default 10 s): stops the background boot retries and waits for usage events still being delivered, keeping Node alive meanwhile, so it can be awaited in a shutdown handler.
- Every failure passed to `onError` is also logged with `console.warn("[lago-x402] <where> failed: <message>")`, so none is silent when no `onError` is set; a throwing `onError` is ignored.
- x402 v2 wire layer (internal, not exported yet): renders Lago gate-check challenges as `PAYMENT-REQUIRED` (with a `sign-in-with-x` challenge bound to the configured origin) and settled purchases as `PAYMENT-RESPONSE`; decodes `PAYMENT-SIGNATURE` and `SIGN-IN-WITH-X` without ever surfacing their contents in errors or logs.
- The gate (internal, not exported yet): answers each protected request from Lago's gate check (402 challenge, 401 sign-in refusal, 403/409/503, or serve), matches a payment against a fresh menu before forwarding it to Lago's credit purchase (a changed amount, pay-to or terms is a fresh 402, never an underpayment), retries a lost purchase answer once, and never answers 402 once money may have moved.
- Local config validation (internal, not exported yet): rejects bad origins, API URLs, route names, amounts, wallet limits and sign-in statements before any network call, without ever echoing the API key.
- Bazaar discovery: a route flagged `discoverable` declares how it is called (`discovery`: `method`, `queryParams` or `bodyType` + `body`, `inputSchema`, `output`; static routes only, `method` comes from config, never from the request). Its 402 carries the official `bazaar` extension and the payment forwarded to Lago carries the same one, so the facilitator catalogues the resource when it settles. Boot refuses an invalid declaration and, per the Bazaar spec's rules, an invalid `resource.serviceName`, `tags`, `iconUrl` or `description` (over 500 characters) instead of letting the facilitator drop them silently.
- `lago-x402/express`: `lagoX402(x402, route)`, Express middleware for Express 4.21+ and 5, attached per route through Express's own router (`app.post("/v1/generate", lagoX402(x402, "generate"), handler)`), so the gate never decides on a path of its own. The handler reports usage with `res.locals.lagoUsage = n`; it is read once the response has finished (or when the client goes away after the headers were sent), and a status of 400 or more sends no event. Served responses carry `PAYMENT-RESPONSE` after a payment and get `private` merged into whatever `Cache-Control` the handler sends. An unknown route name throws `LagoX402ConfigError` when the middleware is attached; the promise `createLagoX402` returns can be passed directly (each request waits for it, and answers 503 `unavailable` if it rejected). Nothing is ever thrown into Express (Express 4 does not catch a rejected middleware): an unexpected failure answers 503 `unavailable` and never serves. `express` is an optional peer dependency and only its types are imported.
- `lago-x402/hono`: `lagoX402(x402, route)`, Hono middleware for Hono 4.6+ on Node (served by `@hono/node-server`), attached per route through Hono's own router (`app.post("/v1/generate", lagoX402(x402, "generate"), handler)`), so the gate never decides on a path of its own. The handler reports usage with `c.set("lagoUsage", n)`, typed by `LagoX402Variables` (`new Hono<{ Variables: LagoX402Variables }>()`). Under `@hono/node-server` the call is billed once the Node response has gone out (or when the client goes away after the headers were sent), with the status that went out; without Node bindings (`app.request()`) it is billed as soon as the middleware has the final response. A status of 400 or more, including Hono's 500 for a throwing handler, sends no event. Served responses carry `PAYMENT-RESPONSE` after a payment and get `private` merged into whatever `Cache-Control` the handler sends, including a `fetch()` response with immutable headers (rebuilt, keeping a 204/205/304 without a body); a response that cannot carry them (no HTTP status, as `Response.error()`) is replaced by 503 `unavailable`. The gate's own answers keep headers an earlier middleware set (CORS) but never let them make a 402 cacheable. An unknown route name throws `LagoX402ConfigError` when the middleware is attached; the promise `createLagoX402` returns can be passed directly (each request waits for it, and answers 503 `unavailable` if it rejected). `hono` is an optional peer dependency and only its types are imported.
