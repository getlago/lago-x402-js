## [Unreleased]

### Added

- `createLagoX402(config)`: validates the config, then checks every route against Lago before it serves. The billable metric must sum the `value` property (`sum_agg`, `field_name: "value"`, no expression, not recurring), and a gate check without sign-in must answer a challenge with sign-in chains (a lago-api with sign-in-with-x on gate checks). A route Lago refuses rejects the boot with one `LagoX402ConfigError` naming every refused route and its reason, reported first (`onError(err, "boot")` and the log line) so the refusal is never silent, even when the promise is only awaited by a request; an invalid config rejects at once and is not reported. A route Lago cannot be reached for (5xx, 408, 429, timeout, network error, facilitator outage) answers 503 `unavailable` and is retried in the background (1 s doubling to 60 s, on timers that never keep the process alive; a check in flight holds it until it ends, at most twice `gateCheckMs`) until it becomes active, or is refused for good if Lago then refuses it.
- The gate: answers each protected request from Lago's gate check (a 402 challenge, a 401 sign-in refusal, 403/409/503, or serve). A request without credentials gets a 402; a request signed in with `SIGN-IN-WITH-X` is served from the agent's credits when Lago passes it; a paid request (`PAYMENT-SIGNATURE`, which wins over a sign-in) is matched against a fresh offer before it is forwarded to Lago's credit purchase, so a changed amount, pay-to or terms gets a fresh 402 (`stale_challenge`) and never an underpayment. A lost or 5xx purchase answer and `credit_grant_failed` are retried once with the identical request within the 45 s budget, and nothing that may follow a settled payment is ever a 402: it is 503 `payment_pending` with `Retry-After` instead. Anything the gate cannot read before a payment is forwarded fails closed as 503 `unavailable`.
- A settled payment serves one request. Each credit purchase carries a new random `idempotency_key`, and Lago answers a payment it already recorded (`replayed`) only under the key it was recorded with, so a settled payment read from the chain, signature included, cannot be presented again and served on its payer's subscription. The gate serves a replay on its own retry of the credit purchase after a lost answer, a 5xx or `credit_grant_failed`; a settled payment presented in a new request, or a payment already recorded against an invoice, gets 409 `payment_already_settled` with `Cache-Control: no-store`, no `PAYMENT-RESPONSE`, no usage event and no report. A pending one still gets 503 `payment_pending` with `Retry-After`. After `payment_pending`, an agent waits and signs in to use the credits it bought instead of resending the payment.
- x402 v2 wire format: Lago's gate-check challenges are rendered as `PAYMENT-REQUIRED` (`Cache-Control: no-store`, body `{}`), with a `sign-in-with-x` challenge whose `domain` and `uri` come from the configured `origin`, never from request headers, and a fresh 16-byte nonce in every 402. Settled purchases are rendered as `PAYMENT-RESPONSE`. `PAYMENT-SIGNATURE` and `SIGN-IN-WITH-X` are decoded without their contents ever reaching an error or a log line.
- Config validation before any network call: bad origins, API URLs, route names, amounts, wallet limits, timeouts and sign-in statements are rejected with a `LagoX402ConfigError` naming the route and the reason, never echoing a config value (the API key least of all).
- Usage events: one `POST /events` per served call with a status below 400, sent after the response has gone out and never batched, carrying the usage the handler reported as `properties.value` and the route's wallet as `target_wallet_code`. Its `transaction_id` (a UUID) and `timestamp` (seconds with millisecond precision, and never earlier than the `subscription_started_at` Lago answers the credit purchase or gate check with, so a server clock lagging Lago's never dates a call before its subscription; the serve time from a Lago that sends none) are fixed when the call is served and resent unchanged on every retry; Lago's duplicate answer counts as delivered. Network errors, timeouts, 5xx, 408 and 429 are retried (4 attempts, 0.5/1/2 s backoff with ±20 % jitter); at most 16 events are in flight and 1,000 queued. A served call whose handler reports no usage or an invalid one, or whose read throws, is billed the route's `fallbackUsage` (required, a positive number of the metric's units) and reported as `usage.extract`, so a forgotten report never serves a call for free.
- `x402.close({ timeoutMs })` (default 10 s): stops the background boot retries and waits for usage events still being delivered, keeping Node alive meanwhile, so it can be awaited in a shutdown handler.
- Every failure passed to `onError` is also logged with `console.warn("[lago-x402] <where> failed: <message>")`, so none is silent when no `onError` is set; a throwing `onError` is ignored.
- Bazaar discovery: a route flagged `discoverable` declares how it is called (`discovery`: `method`, `queryParams` or `bodyType` + `body`, `inputSchema`, `output`; static routes only, `method` comes from config, never from the request). Its 402 carries the official `bazaar` extension and the payment forwarded to Lago carries the same one, so the facilitator catalogues the resource when it settles. Boot refuses an invalid declaration and, per the Bazaar spec's rules, an invalid `resource.serviceName`, `tags`, `iconUrl` or `description` (over 500 characters) instead of letting the facilitator drop them silently.
- `lago-x402/express`: `lagoX402(x402, route)`, Express middleware for Express 4.21+ and 5, attached per route through Express's own router (`app.post("/v1/generate", lagoX402(x402, "generate"), handler)`), so the gate never decides on a path of its own. The handler reports usage with `res.locals.lagoUsage = n`; it is read once the response has finished (or when the client goes away after the headers were sent), and a status of 400 or more sends no event. Served responses carry `PAYMENT-RESPONSE` after a payment and get `private` merged into whatever `Cache-Control` the handler sends. An unknown route name throws `LagoX402ConfigError` when the middleware is attached; the promise `createLagoX402` returns can be passed directly (each request waits for it, and answers 503 `unavailable` if it rejected). Nothing is ever thrown into Express (Express 4 does not catch a rejected middleware): an unexpected failure answers 503 `unavailable` and never serves. `express` is an optional peer dependency and only its types are imported.
- `lago-x402/hono`: `lagoX402(x402, route)`, Hono middleware for Hono 4.6+ on Node (served by `@hono/node-server`), attached per route through Hono's own router (`app.post("/v1/generate", lagoX402(x402, "generate"), handler)`), so the gate never decides on a path of its own. The handler reports usage with `c.set("lagoUsage", n)`, typed by `LagoX402Variables` (`new Hono<{ Variables: LagoX402Variables }>()`). Under `@hono/node-server` the call is billed once the Node response has gone out (or when the client goes away after the headers were sent), with the status that went out; without Node bindings (`app.request()`) it is billed as soon as the middleware has the final response. A status of 400 or more, including Hono's 500 for a throwing handler, sends no event. Served responses carry `PAYMENT-RESPONSE` after a payment and get `private` merged into whatever `Cache-Control` the handler sends, including a `fetch()` response with immutable headers (rebuilt, keeping a 204/205/304 without a body); a response that cannot carry them (no HTTP status, as `Response.error()`) is replaced by 503 `unavailable`, or after a payment by 503 `payment_pending` with `Retry-After`, reported as `gate.purchase`. The gate's own answers keep headers an earlier middleware set (CORS) but never let them make a 402 cacheable. An unknown route name throws `LagoX402ConfigError` when the middleware is attached; the promise `createLagoX402` returns can be passed directly (each request waits for it, and answers 503 `unavailable` if it rejected). `hono` is an optional peer dependency and only its types are imported.
- `lago-x402/next`: `withLagoX402(x402, route, handler)`, a wrapper for Next.js 16 App Router route handlers on the Node runtime (`export const POST = withLagoX402(x402, "generate", async (req) => …)`), so the gate never decides on a path of its own. The handler reports usage by returning `{ response, usage }` (`LagoX402Result`); a bare `Response` reports none, so a served status below 400 is billed the route's `fallbackUsage` and reports `usage.extract`. The call is billed through Next's `after()`: the event goes out once the response has gone out, the response never waits for its delivery, and the delivery is `after()` work that Next holds past the request's end. This was verified with a real `next build && next start`, where a SIGTERM exits only once Lago has answered the event. On serverless, the function's `maxDuration` bounds the delivery (not tested here). Should `after()` throw (outside a request scope), the call is billed at once instead and nothing is thrown. A status of 400 or more sends no event; a handler that throws, or returns no `Response`, throws to Next (its 500) and is billed nothing. Served responses carry `PAYMENT-RESPONSE` after a payment and get `private` merged into whatever `Cache-Control` the handler sends, including a response with immutable headers (`fetch()`, `Response.redirect()`: rebuilt, keeping a 204/205/304 without a body); one that cannot carry them (no HTTP status, as `Response.error()`) is replaced by 503 `unavailable`, or after a payment by 503 `payment_pending` with `Retry-After`, reported as `gate.purchase`. An unknown route name throws `LagoX402ConfigError` when the handler is wrapped; the promise `createLagoX402` returns can be passed directly, from module scope (each request waits for it, and answers 503 `unavailable` if it rejected). `next` (16) is an optional peer dependency, and only its `after` is imported.
- An ESM package for Node `>=22.12` (tested on 22, 24 and 26) with `.d.ts` types, which a CommonJS app can `require()`. The build ships no source maps (they pointed at `src/`, which is not published).
- Verified: no secret ever leaks. A security suite drives every failure the middleware handles (each leg's refusals and every row of the README's error table, malformed and oversized headers, timeouts, a lost purchase answer, usage report and delivery failures, refused and unreachable boots, invalid configs) through the core and through the Express 4/5, Hono and Next adapters over real HTTP, with `PAYMENT-SIGNATURE` and `SIGN-IN-WITH-X` headers built by the official x402 clients, and Lago answers carrying planted free text. No response, `onError` argument (`message`, `stack`, JSON, `util.inspect`, own properties), boot rejection, usage event or `console` call carries the API key, either header's value, the payment's signature or EIP-3009 nonce, the sign-in's signature (not even the 10 characters V8's `JSON.parse` error would quote), a handler's exception text or Lago's free text, and every log line is a `[lago-x402] <where> failed: <message>` report.
- `npm run test:package` (run in CI on Node 22, 24 and 26 and on 22.12.0, the oldest supported, after the build): packs the package with `npm pack`, checks it holds only `package.json`, `dist/`, `README.md`, `CHANGELOG.md` and `LICENSE`, that `dist` imports nothing but Node built-ins, its own files, `@x402/core` and the optional peers, and that a `"type": "commonjs"` app can `require()` (and `import()`) `lago-x402`, `lago-x402/express`, `lago-x402/hono` and `lago-x402/next`, getting exactly the documented exports, one module instance shared by the subpaths.
- `npm run test:live` (skipped unless `LAGO_API_URL`, `LAGO_API_KEY` and `X402_BUYER_EVM_PRIVATE_KEY` are set) runs the three legs against a real Lago with a funded Base Sepolia buyer, through a loopback proxy that records the usage events the middleware sends: a 402 that offers only Base Sepolia and Solana devnet (anything else aborts before signing), a top-up paid by an agent without sign-in and served with `PAYMENT-RESPONSE` (should Lago still be settling it, the agent waits and signs in for its credits instead of resending the payment), the same key signing in and served from its credits without paying, the paid call's `PAYMENT-SIGNATURE` sent again and refused with 409 `payment_already_settled`, neither served nor billed, both usage events found in Lago and billed, with their timestamps 5 s behind the host's clock (`LIVE_EVENT_CLOCK_OFFSET_MS`) and the agent's subscription from an earlier run terminated first, the wallet's ongoing usage rising, and how many distinct Solana fee payers ten gate checks offer. It pays `LIVE_TOP_UP_CENTS` (3¢ by default) once per run. `scripts/live-setup.mjs` creates what it needs through Lago's API only, idempotently (a `sum_agg` metric on `value`, a usage-only USD plan whose charge accepts target wallets, the x402 connection with `LIVE_ORIGIN` allowed), printing only codes, statuses and Lago's error codes.
- Documentation and release process: the README (setup in Lago, quickstarts for Express, Hono and Next.js, configuration, the error table, why a payment serves one request, rate limiting in front of the gate, measured behaviours and limitations, guidance for agent builders), `CONTRIBUTING.md`, `SECURITY.md` and `RELEASING.md`. Tagging `vX.Y.Z` runs `.github/workflows/publish.yml`: a check that the repository is public and that the tag names `package.json`'s `X.Y.Z` version and a commit on `main`, the CI workflow itself as the gate, one build (no dependency install script runs, every dependency's registry signature is verified) packed into the tarball that is both published and attached to the GitHub release, and `npm publish --provenance` of that tarball through npm trusted publishing (OIDC, no token) behind the protected `npm` environment, from a job that checks out and installs nothing. No release job reads the Actions cache, and no checkout keeps the `GITHUB_TOKEN`. Every action is pinned to a full commit SHA, and Dependabot keeps the pins (once a release is a week old) and the dev dependencies fresh.

### Security

- The runtime dependency `@x402/core` is required at `^2.29.0`, its first release on zod `^4.6.6`, so no install of `lago-x402` can resolve a zod below 4.6.6 through it, even from a lockfile that already holds `@x402/core` 2.28. Those zod versions can exhaust memory while validating oversized constrained collections (GHSA-mrhx-c7xc-m3w5, CVE-2023-54404, high). `lago-x402` does not import zod itself.
